# 案例：练习对话里「点评」重复渲染 —— 面试口述稿

> 用途：按「发现问题 → 排查 → 根因 → 方案 → 验证」顺序讲清楚一条完整链路，适合后端/全栈/Agent 方向面试中的项目深挖。

项目目录与文档地图：[`docs/README.md`](../README.md)。

---

## 一、问题是怎么被发现的（现象）

我在做「面经 Agent」的练习对话功能时，用户答完题后，助手会给出**评分 + 点评 + 标准答案**。

线上表现是：**同一条助手消息里，「点评」下面的结构化内容（答对、遗漏、混淆点）出现了两遍**，几乎逐字重复。用户截图里用红框标出了两段相同的列表。

第一印象容易怀疑：**是不是流式 SSE 把 `final_answer` 推了两次？** 或者前端 Markdown 渲染了两次？这需要靠日志和代码路径来证伪或证实。

---

## 二、我当时的初步假设与如何缩小范围

1. **假设 A：前端重复渲染**  
   例如同一条消息被 append 两次，或某个组件既渲染了 `content` 又渲染了子字段。  
   **做法**：看这条气泡是不是只对应一条 `agent_finish` / 一条历史记录；若是单条消息内重复，更可能是**字符串本身就有两段相同结构**。

2. **假设 B：后端 SSE 重复推送**  
   **做法**：看 Network 或后端日志里 `agent_finish` 是否发了两次、payload 是否相同。

3. **假设 C：后端拼出来的最终正文就带了重复**  
   流式阶段可能已经输出过一版，最后又用工具真值「重建」时**又拼了一层**。  
   **做法**：对照终端/日志里 `DeepSeek最终返回` 的 `preview` 与数据库里落库的 `full_content`，看重复是「模型就写了两遍」还是「我们在代码里拼了两遍」。

这次问题里，日志里有一句：**「使用 submit_answer 真值重建最终正文」**，且 preview 里已经能看到完整的「点评 + 列表」，这提示我要重点看 **`submit_answer` 之后如何组装最终展示字符串**。

---

## 三、调试过程（具体怎么查）

1. **看用户界面**  
   重复发生在**同一条气泡**的「点评」区块内部，不是两条消息叠在一起 —— 先倾向于「单字符串内容重复」而不是「两条事件」。

2. **看后端日志**  
   在 `interviewer_agent` 的 `chat_stream` 路径上，有日志记录最终正文长度、preview。  
   对照发现：最终发给前端的正文里，**既有一段 narrative 形式的点评，后面又跟了一套「✅ 答对 / ✗ 遗漏 / ⚠ 混淆点」列表** —— 两套内容语义一致，像同一数据用了两种模板各输出一次。

3. **代码走读：谁负责拼最终正文？**  
   找到评分类回合里，在 `submit_answer` 工具执行完成后，会用工具返回的 JSON **重建**助手最终回复（见下文「辨析」：这和「适配器」「调了几次 agent」不是同一回事）。

4. **精读拼接函数**  
   在 `_build_eval_answer_from_payload`（或等价逻辑）里，流程大致是：  
   - 先写入评分行；  
   - 再写入 **`feedback` 字段**（模型/工具里往往已经是完整 Markdown，含「点评」和 ✓✗⚠ 列表）；  
   - 然后又根据 **`strong_points` / `missed_points` / `error_points`** 再拼一遍「✅ 答对」「✗ 遗漏」「⚠ 混淆点」。  

   当 `feedback` 已经内嵌了和这三个数组**相同语义**的内容时，用户就会看到**点评区重复两遍**。

---

## 四、根因结论（一句话 + 展开）

**根因：`feedback` 与结构化字段（strong/missed/error）在业务上表达的是同一套信息；拼接逻辑没有做「已包含则跳过」，导致最终字符串里同一套列表出现两次。**

补充说明：

- **不是**「`final_answer` SSE 推错推了两次」这种低级重复推送（本案例核心是**内容拼接**）。

### 辨析：加了流式适配器之后，「重建正文」到底还要不要？

容易混在一起的三件事，建议面试时分开说：

| 概念 | 解决什么 |
|------|----------|
| **DeepSeek / hello_agents 流式适配器** | 把 **reasoning（思考）** 和 **content（正文）** 分成不同事件类型，前端好展示、不乱炖。 |
| **评分类「抑制正文 llm_chunk」** | 这一类产品策略下，用户**几乎看不到**主模型在 content 里边生成边改的段落，只在 `agent_finish` 给一整块正文。 |
| **`submit_answer` 后「用工具 JSON 拼最终正文」** | 用工具返回里的 **score、feedback、标准答案、SM-2 下次复习** 等，拼成**固定版式**的一条助手消息；和「有没有两次调主 Agent」**无关**。 |

**为什么说「不是防二次调用 agent」？**  
一轮对话里仍然可以是 **一次 ReAct 循环**：主模型决定调工具，工具内部再去跑 **结构化评估**（例如独立的评估 LLM / 服务），返回 JSON。适配器**不会**把「工具里的评估结果」和「主模型在 content 里随手写的那几段话」变成同一个数据源——它们本来就是两条链路上的输出。

**那为什么代码里还保留重建（不只用主模型 final 字符串）？** 常见原因包括（按产品取舍，不是教条）：

1. **展示与落库同源**：学习记录、SM-2、标准答案来自工具链；用户看到的正文若直接由工具 JSON 拼出来，和库里逻辑一致，少一层「模型复述跑偏」。  
2. **固定模板**：例如「📚 标准答案」「📌 下次复习」「底部操作提示」——主模型 final 可能漏写或换说法，工具返回里才有稳定字段。  
3. **和「抑制正文 chunk」配合**：前端没流式正文时，`agent_finish` 必须有一块完整内容；用工具拼好的模板比依赖主模型自由发挥更可控。

若产品上要**去掉重建**，需要同时想清楚：是否取消抑制、是否强约束 prompt 让 final 与工具 JSON 完全一致、漏字段时谁兜底——那是另一条设计方案，**不是因为「有了适配器」就自动不需要重建**。

本 bug 要修的是：**重建时在 `feedback` 已含列表的情况下又拼了一遍 strong/missed/error**，属于拼接重复，不是否定整条重建动机。

---

## 五、解决方案（设计取舍）

**（演进）** 若产品要求聊天里**只显示模型的 final answer**：可直接去掉「用 `submit_answer` JSON 覆盖 `agent_finish` 正文」，重复拼接问题随重建路径一并消失；库里的评分与 SM-2 仍以工具为准，与气泡展示解耦。

**（历史方案）** 在仍采用「工具拼正文」时，目标是：在保留「以工具真值为准」的前提下，消除重复展示。

**策略**：对 `feedback` 做轻量启发式判断 —— 若已同时出现「答对/✓」与「遗漏/✗」等列表化点评特征，且长度足够，则认为 **narrative 已覆盖结构化列表**，**不再**追加 `strong_points` / `missed_points` / `error_points` 三块。

**取舍说明**：

- 用启发式而不是大改 schema，是因为工具返回里 **`feedback` 与数组字段常由同一评估逻辑生成**，重复是拼接策略问题，不必立刻动协议。  
- 若未来 `feedback` 只保留短评、要点全靠数组，启发式会判定为「未内嵌列表」，**仍走原来的结构化追加**，兼容旧形态。

---

## 六、验证与回归

1. **手工**：再走一轮练习对话，确认「点评」下只出现一套列表。  
2. **单测**：对 `_feedback_already_has_eval_lists` 这类纯函数写几条用例 —— 空/短文本、`仅评分细则`、以及「带 ✓✗ 的完整点评」三种，防止以后改字符串规则时回归。

---

## 七、面试时可用的「升华」表述（可选）

- **系统性思维**：先区分「重复事件」与「重复内容」，再用日志锁定数据是在哪一层被复制。  
- **Agent 工程**：工具返回是 source of truth，流式输出是 UX；最终展示要以工具为准，但要避免**同一真值用两种模板渲染两遍**。  
- **可维护性**：把「是否已内嵌列表」抽成命名清晰的函数 + 单测，比散落在 `if` 里更安全。

---

## 八、30 秒超短版（电梯陈述）

「练习对话评分后，点评重复。排查发现不是 SSE 双推，而是 `submit_answer` 重建正文时，`feedback` 里已经写了完整点评列表，代码又根据 strong/missed/error 拼了一遍。用启发式：feedback 已含答对/遗漏结构就跳过重复拼接，并补了单测。流式适配器管的是思考/正文分流；重建是用工具 JSON 拼固定展示，和防不禁『两次调 agent』不是一回事，是否保留重建是产品与一致性取舍。」

---

*历史实现：`chat_stream` 曾用 `submit_answer` 的 JSON 重建聊天正文（并因此出现过 `feedback` 与数组字段重复拼接的问题）。当前产品选择为：**聊天区仅展示 ReAct `agent_finish` 的模型终稿（final answer）**，不再用工具返回覆盖正文；学习记录仍以工具落库为准。*
