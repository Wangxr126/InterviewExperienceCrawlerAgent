# 题库链路与表结构设计

更新时间：2026-05-09  
文档状态：设计草案（与 Doc 06 召回策略对齐）  
存储：所有表均建于 **MySQL**，由 Java Spring Boot 管理。

---

## 1. 设计目标

这一版不沿用现有的 Stage1 / Stage2 逻辑，也不保留 `raw_answer`。目标是按真实流程重建表结构：先爬链接，再抓取页面，再调用远程 LLM 提取结构化题目，最后落到题库主表和向量层。

这版设计遵循下面几条原则：

1. 链接、任务、抓取产物、抽取结果、题目事实、向量投影分层存放。
2. 语义字段不设默认值，尤其是 `difficulty`、`question_type`、`company`、`position`、`business_line`。
3. 标签标准化不作为首版必选层，先把 `tags_json` 作为结构化结果缓存。
4. `q_id`、`source_link_id`、`task_id`、`run_id`、`item_id`、`vector_id` 都由应用层生成，不使用自增主键做业务标识。
5. 主表只存当前可查询快照，不存阶段性中间结果和历史全文。
6. 唯一去重只发生在帖子链接这一层（`source_links.url`）；题目主表的 `duplicate_group_id` 是相似归组，不是去重维度。
7. 抽取阶段的"是否保留"为业务过滤，展示阶段的"是否折叠"为展示聚合，两者分开处理。
8. `questions` 表允许手动录入题目，此时 `task_id` 和 `run_id` 可以为空。

## 2. 整体流程

### 2.1 数据流

```
source_links -> crawl_tasks -> crawl_artifacts -> question_extraction_runs -> extracted_question_items -> questions -> question_vectors
```

### 2.2 各层职责

| 层级 | 表名 | 作用 | 是否首版必需 |
|---|---|---|---|
| 来源层 | `source_links` | 统一管理来源链接、帖子链接去重和页面元信息 | 必需 |
| 抓取层 | `crawl_tasks` | 记录每次抓取、重试、解析任务状态 | 必需 |
| 产物层 | `crawl_artifacts` | 存储抓取产物（原始 HTML、解析文本等），作为抽取层的输入 | 必需 |
| 抽取层 | `question_extraction_runs` | 记录一次远程 LLM 结构化抽取的输入、输出和状态 | 必需 |
| 明细层 | `extracted_question_items` | 记录一次抽取里产生的多道题明细 | 必需 |
| 事实层 | `questions` | 题库 canonical 主表，保存当前快照 | 必需 |
| 检索层 | `question_vectors` | 题目向量和检索 payload 投影 | 必需 |

### 2.3 这版明确不前置的表

本版先不强制引入下面这些表：

- `question_versions`
- `tags`
- `question_tag_rel`
- `question_relations`
- `question_sources`

原因：当前主流程是一轮远程 LLM 结构化提取，后续不打算频繁回写历史版本；标签也先作为 JSON 缓存即可。

### 2.4 抽取阶段的题外内容过滤

建议把规则写成明确的抽取约束，不要只靠一句 prompt 兜底：

| 类别 | 处理方式 | 例子 |
|---|---|---|
| 明确题面 | 抽取 | 请做一下自我介绍、讲讲你这个项目、这个接口怎么设计、这题的时间复杂度是多少 |
| 追问 / 澄清 | 抽取 | 为什么这么做、还有别的方案吗、如果并发更高怎么办 |
| 纯叙述 / 感想 | 跳过 | 今天面试整体还不错、面试官很友好、我有点紧张 |
| 流程说明 / 过场 | 跳过 | 先聊项目再聊算法、最后问了薪资、下面是面试复盘 |
| 无法独立作答的片段 | 跳过 | 只是一句项目拷打、只是一个自我介绍标题、没有明确问法的背景描述 |

推荐做法：让 LLM 只输出"可独立作答的题目"，其余片段不进入 `extracted_question_items`；如果需要审计，可以把 `skipped_segments_summary` 之类的摘要放进 `question_extraction_runs.output_json` 里。

## 3. 核心表设计

### 3.1 `source_links`

一条来源链接一行，只保留一条真正的 URL 作为唯一入口。写入前在代码里先做归一化，库里不再拆 `original_url` / `canonical_url` 两列。这里的 `url` 是全链路唯一去重点，后续任务、抽取和题目都只挂接，不再拿题库内容做去重键。

| 字段名 | 类型 | 约束 | 写入时机 | 更新时机 | 说明 |
|---|---|---|---|---|---|
| `source_link_id` | `TEXT` | 主键，非空 | 新链接首次发现时生成 | 不更新 | 来源链接业务主键 |
| `url` | `TEXT` | 非空，唯一 | 发现链接时写入 | 不更新 | 归一化后的真正 URL |
| `source_platform` | `TEXT` | 可空 | 能识别平台时写入 | 平台识别修正时更新 | 如 nowcoder、xhs 等 |
| `title` | `TEXT` | 可空 | 抓取标题后写入 | 标题回填时更新 | 页面标题 |
| `published_at` | `DATETIME` | 可空 | 能识别帖子原始发布时间时写入 | 发布时间回填时更新 | 帖子 / 页面本身的时间 |
| `discovered_at` | `DATETIME` | 非空 | 发现链接时写入 | 不更新 | 第一次发现这个 URL 的时间 |
| `crawled_at` | `DATETIME` | 可空 | 实际抓取完成后写入 | 每次重新抓取时更新 | 最近一次抓取时间 |
| `status` | `TEXT` | 非空 | 由调用方显式写入 | 状态变化时更新 | 枚举：pending / crawled / parsed / ingested / abandoned / failed |
| `source_meta_json` | `TEXT` | 可空 | 发现或解析时写入 | 元信息补充时更新 | 页面级补充信息 |

### 3.3 `crawl_artifacts`

存储抓取任务产出的**解析后文本**，作为 LLM 抽取层的直接输入底料。

**关于原始 HTML 的取舍**：不保存原始 HTML，原因如下：
- 存储成本高，HTML 通常比清洗后文本大 3~10 倍。
- 重新抓取的成本低，绝大多数情况下重爬比回放 HTML 更简单。
- 解析 + 清洗逻辑本身也在迭代，保存旧 HTML 不能保证重跑出相同的解析结果。

**为什么仍然需要这张表（保存解析文本）**：
- Prompt Playground 需要对同一段内容反复跑不同 prompt，此时不能依赖重新爬取（页面可能被删除或修改）。
- `question_extraction_runs.input_json` 存的是"LLM 实际收到的输入"（prompt + content 拼合后），不是纯净的页面文本；两者需要分开存。
- 一个 `artifact` 可以被多次实验（不同 prompt、不同模型）复用，是"实验底料"。

| 字段名 | 类型 | 约束 | 写入时机 | 更新时机 | 说明 |
|---|---|---|---|---|---|
| `artifact_id` | `TEXT` | 主键，非空 | 产物生成时写入 | 不更新 | 产物业务主键 |
| `task_id` | `TEXT` | 非空，外键 | 产物生成时写入 | 不更新 | 关联抓取任务 |
| `source_link_id` | `TEXT` | 非空，外键 | 产物生成时写入 | 不更新 | 关联来源链接，便于回溯 |
| `parsed_text` | `TEXT` | 非空 | 解析完成后写入 | 不更新 | 清洗后的纯文本，LLM 抽取的直接输入底料 |
| `content_hash` | `TEXT` | 非空 | 写入时计算 | 不更新 | 内容指纹，用于幂等校验和变更检测 |
| `char_count` | `INTEGER` | 可空 | 写入时计算 | 不更新 | 文本字符数，方便估算 token 用量 |
| `parse_method` | `TEXT` | 可空 | 写入时记录 | 不更新 | 解析方式，如 trafilatura / readability / custom |
| `artifact_meta_json` | `TEXT` | 可空 | 写入时补充 | 元信息变化时更新 | 编码、语言、结构信息等扩展字段 |
| `created_at` | `DATETIME` | 非空 | 写入时生成 | 不更新 | 创建时间 |

|---|---|---|---|---|---|

| `source_link_id` | `TEXT` | 非空，外键 | 发起抽取时写入 | 不更新 | 来源链接 |
| `task_id` | `TEXT` | 非空，外键 | 发起抽取时写入 | 不更新 | 关联抓取任务 |
| `artifact_id` | `TEXT` | 可空，外键 | 发起抽取时写入 | 不更新 | 关联抓取产物，是本次抽取的直接输入 |
| `input_json` | `TEXT` | 非空 | 发起抽取时写入 | 输入变化时更新 | 直接保存本次抽取输入（通常来自 artifact 内容） |
| `model_provider` | `TEXT` | 非空 | 发起抽取时写入 | 模型切换时更新 | 如 openai、anthropic、deepseek 等 |
| `model_name` | `TEXT` | 非空 | 发起抽取时写入 | 模型切换时更新 | 具体模型名 |
| `prompt_version` | `TEXT` | 非空 | 发起抽取时写入 | 提示词版本切换时更新 | 提示词版本号 |

| `output_json` | `TEXT` | 可空 | 抽取成功时写入 | 失败重试时更新 | LLM 原始结构化输出 |
| `output_hash` | `TEXT` | 可空 | 输出完成后计算 | 输出变化时更新 | 输出指纹 |

### 3.6 `questions`

这是 canonical 题库主表。它只保存当前快照，不保存原始阶段产物，不保存历史全文。

**关于来源外键的说明**：题目可以来自爬虫链路（有 `task_id` 和 `run_id`），也可以手动录入（无 `task_id` 和 `run_id`）。因此 `task_id` 和 `run_id` 设为可空，通过 `origin_item_id` 可以完整回溯到抽取链路。

### 3.7 `question_vectors`

向量层是派生层，只负责检索和排序，不承担事实源职责。首版默认一题一条题干向量，后续如有需要再补答案向量或组合向量。

| 字段名 | 类型 | 约束 | 写入时机 | 更新时机 | 说明 |
|---|---|---|---|---|---|
| `vector_id` | `TEXT` | 主键，非空 | 生成向量时写入 | 不更新 | 向量记录主键 |
| `q_id` | `TEXT` | 非空，外键 | 生成向量时写入 | 题目重建时更新 | 关联题目 |
| `vector_role` | `TEXT` | 非空 | 生成向量时写入 | 召回角色变化时更新 | 如 question_semantic、answer_semantic、composite_semantic |
| `source_text_kind` | `TEXT` | 非空 | 生成向量时写入 | 输入文本构成变化时更新 | 如 question_text、answer_text、question_plus_tags |
| `source_text` | `TEXT` | 非空 | 生成向量时写入 | 向量重算时更新 | 真正送入 embedding 的文本快照 |
| `source_text_hash` | `TEXT` | 非空 | 生成向量时计算 | 不更新，除非重算 | 文本指纹 |
| `embedding` | `VECTOR/FLOAT[]/BLOB` | 非空 | 生成向量时写入 | 向量重算时更新 | 具体类型由存储引擎决定 |
| `embedding_model` | `TEXT` | 非空 | 生成向量时写入 | 模型切换时更新 | embedding 模型名 |
| `embedding_dim` | `INTEGER` | 非空 | 生成向量时写入 | 模型切换时更新 | 向量维度 |
| `payload_json` | `TEXT` | 可空 | 生成向量时写入 | 主表过滤字段变化时更新 | 检索过滤和解释信息（含 company、position、difficulty 等） |
| `indexed_at` | `DATETIME` | 非空 | 生成向量时写入 | 重建时更新 | 索引入库时间 |
| `updated_at` | `DATETIME` | 非空 | 生成向量时写入 | payload 或向量变化时更新 | 最近修改时间 |

---

## 4. 关系和约束

### 4.1 主链路关系

| 关系 | 约束 |
|---|---|
| `source_links` -> `crawl_tasks` | 一条来源链接可以对应多次抓取任务 |
| `crawl_tasks` -> `crawl_artifacts` | 一次任务可以产生多个产物（html、text、screenshot 等） |
| `crawl_artifacts` -> `question_extraction_runs` | 一个产物可以触发一次或多次抽取运行（重试、多 prompt 版本） |
| `crawl_tasks` -> `question_extraction_runs` | 通过 `task_id` 直接关联，无需绕道 artifact |
| `question_extraction_runs` -> `extracted_question_items` | 一次抽取运行可以产出多道题 |
| `extracted_question_items` -> `questions` | 一条明细最多映射一条 canonical 题目（`origin_item_id` 唯一） |
| `questions` -> `question_vectors` | 一道题可以有一条或多条向量记录 |

### 4.2 建议唯一约束

| 表 | 建议唯一约束 | 目的 |
|---|---|---|
| `source_links` | `url` | 链接去重 |
| `crawl_tasks` | `task_id` | 任务幂等 |
| `crawl_artifacts` | `artifact_id`；可选 `(task_id, artifact_type, content_hash)` | 产物幂等 |
| `question_extraction_runs` | `run_id` | 抽取运行幂等 |
| `extracted_question_items` | `item_id`、`item_hash` | 明细幂等 |
| `questions` | `q_id`；`origin_item_id`（非空时唯一） | canonical 记录幂等 |
| `question_vectors` | `vector_id`；可选 `(q_id, vector_role)` | 向量唯一性 |

### 4.3 `duplicate_group_id` 与去重的关系

**重要区分**：

- **帖子链接去重**（`source_links.url` 唯一）：防止同一帖子被多次采集入库，这是真正的去重。
- **题目相似归组**（`questions.duplicate_group_id`）：把表述相近的题打上同一个 `group_id`，用于展示时折叠变体题。这**不是去重**，不同组的题仍然各自存在于 `questions` 表中。

`duplicate_group_id` 的写入时机是召回或手动审核时，不是抽取时。初始所有题的 `duplicate_group_id` 为空，代表"尚未归组"。

### 4.4 `question_fingerprint` 说明

`question_fingerprint` 是"标准化题干 + 必要上下文"的指纹（不是原文 hash），只用于调试、统计、相似分析或后续扩展，不作为唯一去重维度。

展示层如果要做"折叠同类题"，可以把 `question_fingerprint` 作为聚类特征之一，再配合 `duplicate_group_id` 和 embedding 相似度做 presentation clustering，但这个动作只发生在展示层，不回写成主表唯一约束。

## 5. 字段策略

### 5.1 不设默认值的字段

下面这些字段都不建议用默认值掩盖空值：

- `difficulty`
- `question_type`
- `company`
- `position`
- `business_line`
- `tags_json`

这些字段的语义是"抽取器明确识别出来的结果"，不是"系统帮你猜一个兜底值"。如果识别不到，就留空。

### 5.2 可以保留技术默认值的字段

- `created_at`
- `updated_at`
- `indexed_at`

### 5.3 这版统一取消的旧字段

- `Stage1` / `Stage2`
- `raw_answer`
- 题库主表里的阶段中间态字段
- 标签字典表和关系表的强制前置设计

---

## 6. 标签策略

首版不强制做 `tags` 和 `question_tag_rel`。原因：当前主流程只有一次远程 LLM 结构化抽取，后续不打算频繁修改标签；在这种前提下，把 `tags_json` 作为缓存字段就足够了。

这版的建议：

1. `extracted_question_items.tags_json` 作为抽取结果缓存（JSON 数组）。
2. `questions.tags_json` 作为 canonical 查询缓存（同格式）。
3. 如果后续标签需要做别名、层级、统计或跨题分析，再补 `tags` 和 `question_tag_rel`。

---

## 7. 向量层设计

### 7.1 首版向量策略

首版只做题干语义向量，即 `vector_role = question_semantic`。这足够支持：

1. 入库查重（相似召回）。
2. 相似题展示。
3. 出题时找近似题。
4. 推荐中的语义补充。

### 7.2 什么时候再补第二条向量

下面这些需求变强后，再考虑补新向量角色：

- 需要按答案反查题目。
- 需要题干 + 答案摘要的混合召回。
- 需要概念锚点或知识点锚点召回。

### 7.3 向量层和事实层的边界

| 层 | 责任 |
|---|---|
| `questions` | 维护题库事实和当前快照 |
| `question_vectors` | 维护语义索引、payload 和排序辅助信息 |

向量层不是事实源，因此可以和主表适度重复过滤字段（`company`、`position`、`difficulty` 等放进 `payload_json`），但不要把版本历史、用户态或流程中间态塞进去。

---

## 8. 最小建表顺序

建议按下面顺序落地：

1. `source_links`
2. `crawl_tasks`
3. `crawl_artifacts`
4. `question_extraction_runs`
5. `extracted_question_items`
6. `questions`
7. `question_vectors`

这样可以保证每一步都是独立闭环，不会把 schema 改造成一次性大迁移。

---

## 9. 本版结论

这一版的核心变化：

- **新增 `crawl_artifacts` 表**：补全链路中的产物层，作为抽取层的直接输入。
- **`questions` 表新增 `duplicate_group_id`**：明确相似归组与帖子链接去重的边界。
- **`questions` 表新增 `source_url`、`source_platform`**：召回层直接可用，避免每次 join `source_links`。
- **`questions.task_id` 和 `run_id` 改为可空**：允许手动录入题目，不强制所有题来自爬虫链路。
- **`questions.tags_json_cache` 改名为 `tags_json`**：与 `extracted_question_items` 保持一致命名。
- `duplicate_group_id` 只是相似归组，不是唯一去重约束，真正的去重仍然在 `source_links.url`。
