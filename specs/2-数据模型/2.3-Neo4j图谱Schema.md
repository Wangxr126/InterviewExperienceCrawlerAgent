## 1. 节点类型

| 节点标签 | 核心属性 | 说明 |
|---|---|---|
| `Domain` | `name`, `description`, `alias_json` | 顶级技术域，手动维护，约 15~20 个 |
| `Concept` | `name`, `description`, `alias_json`, `embedding` | 知识概念，LLM 提取 + 自动建立 |
| `Question` | `id`, `text`, `answer`, `embedding`, `difficulty`, `question_type`, `company`, `position`, `status` | 题目节点 |
| `Tag` | `name` | 标签（与 Concept 独立，Concept 是知识语义，Tag 是分类标签） |
| `Company` | `name` | 公司节点 |
| `Position` | `name` | 岗位节点 |

### 1.1 不用 `level` 属性的原因

`level`（domain/subdomain/concept）不作为存储属性，而作为**图结构的推导结果**：

```
level = 从当前节点到根节点的 BELONGS_TO 跳数
```

这样做的优势：
- 不需要提前分级，层级由图结构自然体现。
- 层级可以随图结构演进而变化，不需要手动维护。
- 查询时用 Cypher 的路径长度过滤即可。

### 1.2 顶级 Domain 种子列表（手动预建）

Domain 按**技术大类**分组，每个 Domain 是一棵独立的概念子树根节点。

| Domain 节点名 | 典型子概念举例 |
|---|---|

**维护原则**：
- Domain 节点**只增不删**（有历史题挂着就保留），可以标记 `deprecated`。
- 新 Domain 需要人工评审后才能加入种子列表。
- LLM 提取的概念**不能**自动创建 Domain 级节点，只能创建 Concept 级节点。

## 2. 关系类型总表

| 关系 | 方向 | 属性 | 说明 |
|---|---|---|---|
| `BELONGS_TO` | `(Concept)→(Concept/Domain)` | `confidence` | 概念的父节点，构建层级结构 |
| `RELATED_TO` | `(Concept)↔(Concept)` | `weight`, `relation_type`, `source` | 概念间横向相关，不区分方向 |
| `COVERS_CONCEPT` | `(Question)→(Concept)` | `confidence` | 题目覆盖的知识概念 |
| `HAS_TAG` | `(Question)→(Tag)` | — | 题目标签 |
| `FROM_COMPANY` | `(Question)→(Company)` | — | 来源公司 |
| `FOR_POSITION` | `(Question)→(Position)` | — | 适用岗位 |
| `VARIANT_OF` | `(Question)→(Question)` | `composite_score`, `vector_sim`, `concept_jaccard`, `method`, `created_at` | 相似变体题（详见 [2.5](2.5-相似归组表.md)） |
| `PREREQUISITE_OF` | `(Concept)→(Concept)` | — | 前置知识关系（如：TCP/IP 是 HTTP 的前置） |

### 2.1 `RELATED_TO` 的 `relation_type` 枚举

| 值 | 含义 | 示例 |
|---|---|---|
| `sibling` | 同属一个父概念的兄弟概念 | IOC 和 AOP 都属于 Spring |
| `complement` | 互相补充的概念 | 索引和查询优化 |
| `implementation` | 实现关系 | DI 是 IOC 的实现方式 |
| `cooccurrence` | 高频共现，来自数据挖掘 | 通过共现批量任务自动建立 |
| `llm_inferred` | LLM 推断的关系 | 通过 LLM 批量推断建立 |

## 3. 索引与约束

### 3.1 唯一约束

```cypher
CREATE CONSTRAINT FOR (d:Domain) REQUIRE d.name IS UNIQUE;
CREATE CONSTRAINT FOR (c:Concept) REQUIRE c.name IS UNIQUE;
CREATE CONSTRAINT FOR (q:Question) REQUIRE q.id IS UNIQUE;
CREATE CONSTRAINT FOR (t:Tag) REQUIRE t.name IS UNIQUE;
CREATE CONSTRAINT FOR (co:Company) REQUIRE co.name IS UNIQUE;
CREATE CONSTRAINT FOR (p:Position) REQUIRE p.name IS UNIQUE;
```

### 3.2 向量索引

```cypher
CREATE VECTOR INDEX `question-embeddings` IF NOT EXISTS
FOR (q:Question) ON (q.embedding)
OPTIONS {indexConfig: {
  `vector.dimensions`: 1536,
  `vector.similarity_function`: 'cosine'
}};

CREATE VECTOR INDEX `concept-embeddings` IF NOT EXISTS
FOR (c:Concept) ON (c.embedding)
OPTIONS {indexConfig: {
  `vector.dimensions`: 1536,
  `vector.similarity_function`: 'cosine'
}};
```

> 维度由 embedding 模型决定，TODO 在 1.3 中间件选型 / 3.4 向量索引流水线 中确定具体模型。

### 3.3 普通索引

```cypher
CREATE INDEX FOR (q:Question) ON (q.status);
CREATE INDEX FOR (q:Question) ON (q.position);
CREATE INDEX FOR (q:Question) ON (q.company);
```

## 4. 与 MySQL 主表的同步策略

| MySQL 操作 | Neo4j 同步动作 |
|---|---|
| `questions` 新增题目 | 创建 `Question` 节点，写入 `HAS_TAG`、`COVERS_CONCEPT`、`FROM_COMPANY`、`FOR_POSITION` 关系 |
| 相似归组任务完成 | 写入 `VARIANT_OF` 关系，同步更新 MySQL `questions.duplicate_group_id` |
| 题目状态变更（hidden/deleted） | 更新 Neo4j `Question` 节点的 `status` 属性 |
| 题目向量重算 | 更新 `Question.embedding`（向量索引自动维护） |

同步通过 **RabbitMQ 事件**驱动，不在主链路同步调用，保证写入性能。详细流程见 [3.2 图谱构建流水线](../3-后台流水线/3.2-图谱构建流水线.md) 与 [3.4 向量索引流水线](../3-后台流水线/3.4-向量索引流水线.md)。

## 5. embedding 字段在 Neo4j vs MySQL 的边界

embedding 向量存在 **Neo4j `Question` 节点的 `embedding` 属性**上并建立 vector index。MySQL 的 `question_vectors` 表（详见 [2.2](2.2-题库主表设计.md)）**不再存储向量本身**，只保留检索辅助信息：

| 保留字段 | 用途 |
|---|---|
| `q_id` | 关联题目 |
| `embedding_model` | 记录向量使用的模型（切换模型时判断是否需要重建） |
| `source_text_hash` | 题干是否变更，是否需要重建向量 |
| `indexed_at` | 向量最后更新时间 |
| `payload_json` | Java 侧结构化过滤字段快照（company、position、difficulty 等） |

向量 float 数组只存 Neo4j，不存 MySQL。
