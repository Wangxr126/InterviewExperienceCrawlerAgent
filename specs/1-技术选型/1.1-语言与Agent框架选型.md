## 1. 选型目标与约束

| 维度 | 目标要求 | 约束条件 |
|---|---|---|
| 业务稳定性 | 支持长期在线运行与故障可恢复 | 初期资源有限，需先单机后扩容 |
| 演进效率 | 支持 Agent、RAG、GraphRAG 快速迭代 | 需要避免框架锁定 |
| 工程治理 | 具备测试、监控、发布、回滚能力 | 最终需支持生产化运维 |
| 可迁移性 | 后续可拆分服务并替换组件 | 兼容多模型供应商 |

## 2. 双语言架构策略

### 2.1 Java + Python 分工明确，从一开始就双栈

本项目采用 **Java 主业务服务 + Python AI 服务**的双语言架构，这不是"未来考虑"而是当前阶段就应落地的架构决定。

**引入 Java 的核心理由**：

| 理由 | 具体场景 | 说明 |
|---|---|---|
| **MQ 削峰** | 爬取任务、LLM 抽取调用 | LLM 调用慢（秒级），高并发时必须通过 MQ 做异步解耦和流量削峰，Java + Spring + RabbitMQ 是这套的标准成熟方案 |
| **企业服务稳定性** | 用户管理、题库 CRUD、会话治理 | 线程池、连接池、背压、GC 调优、JVM 监控在 Java 生态里更成熟，适合长期稳定运行的主链路 |
| **AgentScope 编排调度** | 定时任务、批量抽取、面试流程触发 | Java 侧通过 MQ 和 HTTP 调度 Python 侧的 AgentScope，Java 不做 Agent 逻辑，只做"下发指令 + 收结果" |
| **企业中间件集成** | 统一鉴权、服务注册、配置中心 | Spring 全家桶与治理组件成熟，适合后续对接企业内部系统 |

**Python 继续保留的理由**：

| 理由 | 具体场景 | 说明 |
|---|---|---|
| **AI 生态领先** | LlamaIndex RAG、AgentScope Agent | Python 是 AI/ML 的一等公民，框架迭代快，没有替代 |
| **算法迭代效率** | Prompt 调试、检索策略优化 | Python 的交互式开发和原型速度远超 Java |

### 2.2 双语言分工边界

```
Java (Spring Boot)                      Python (FastAPI / AgentScope / LlamaIndex)
────────────────────────────────────    ────────────────────────────────────────────
用户、鉴权、会话、题库 CRUD             AgentScope 多 Agent 编排（面试、抽题、评分）
MQ 生产者/消费者（RabbitMQ）    HTTP    LlamaIndex RAG、检索、重排、GraphRAG
任务调度（爬取触发、批量抽取）  ←──→   Prompt Playground、实验运行
统一 API 网关                           LLM 调用（OpenAI / DeepSeek / Anthropic）
服务监控、链路追踪、运维治理            向量计算、embedding 生成
```

两侧通过 **HTTP + MQ** 通信，接口契约用 OpenAPI 管理。Java 侧不引入 AI 框架，Python 侧不承担主业务存储和用户态管理。

### 2.3 Python 与 Java 的能力对比

| 比较项 | Java（Spring 生态） | Python（FastAPI 生态） | 本项目分工 |
|---|---|---|---|
| 并发治理 / 连接池 | 成熟，可调优 | 异步高效，但治理靠规范 | Java 承担主业务并发 |
| MQ 集成 | Spring AMQP、Kafka 生态完善 | 可集成，但不是一等公民 | Java 承担 MQ 消费者 |
| AI 框架迭代 | 慢（LangChain4j 等尚不成熟） | 快（LlamaIndex、AgentScope 持续迭代） | Python 承担 AI 层 |
| 类型安全 / 编译期检查 | 强，适合多人协作大型系统 | 需类型标注 + 测试兜底 | Java 承担核心业务逻辑 |
| 运行时调优 / JVM | 工具成熟（JFR、Arthas 等） | 较轻量，诊断链条弱 | Java 承担长期运行治理 |

## 3. 框架决策

### 3.1 已决策：AgentScope + LlamaIndex

经过 MVP 验证（见 Doc 02），当前阶段 Python 侧采用以下组合：

| 层级 | 框架 | 职责边界 |
|---|---|---|
| 检索 / RAG / 索引层 | **LlamaIndex** | 召回路由、向量检索、BM25、混合检索、重排、GraphRAG、数据连接器 |
| Agent 编排 / 角色协作层 | **AgentScope** | 面试 Agent、抽题 Agent、评分 Agent 等角色协作；消息流与执行轨迹记录 |
| 业务 API 层 | **FastAPI** | 用户、会话、题库、鉴权、调度，现阶段主业务服务 |
| 原型 / 局部验证 | **hello-agents** | 适合小范围 PoC，不作为长期主框架 |

**AgentScope 负责"谁在做什么"，LlamaIndex 负责"怎么找到信息"**，两者边界清晰，不互相承担对方的核心职责。

### 3.2 不采用 LangGraph 的原因

| 维度 | LangGraph | AgentScope | 本项目判断 |
|---|---|---|---|
| 核心抽象 | 状态图 / 有向图工作流 | 角色式 Agent + 消息流 | 本项目的核心场景是"有角色的协作流水线"，不是"带 checkpoint 的状态机" |
| 验证状态 | 未验证 | MVP 已验证可运行 | 切换有成本，收益不明确 |
| 学习曲线 | 较高，图式编排概念多 | 中等，角色概念直观 | 当前阶段不应引入额外学习成本 |
| 适合场景 | 复杂的分支路由、人机协作审批流 | 角色协作、出题/评分/复核流水线 | 后者更贴合当前业务主线 |

如果未来需要"带人工审批节点的复杂状态机"，再评估引入 LangGraph。

### 3.3 LlamaIndex Workflows 的备选价值

LlamaIndex 自带的 Workflows（事件驱动工作流）在部分场景下可以替代 AgentScope 的编排能力，优势是只维护一个框架。当出现以下信号时，可以重新评估是否用 LlamaIndex Workflows 替代 AgentScope：

- AgentScope 的版本升级出现不兼容问题
- 需要的编排逻辑用 LlamaIndex Workflows 已经能更简洁地表达
- AgentScope 社区缩减、维护降频

目前不必替换，优先保持已验证的稳定组合。

## 5. 架构决策（第 2 轮）

### 5.1 推荐方案

| 层级 | 推荐技术 | 职责边界 |
|---|---|---|
| 主业务服务层 | **Java + Spring Boot** | 用户、会话、题库 CRUD、鉴权、任务调度、MQ 生产者/消费者 |
| 消息队列层 | **RabbitMQ** | 爬取任务下发、LLM 抽取削峰、异步解耦；Java 侧统一管理 |
| Agent 编排 / 角色协作层 | **Python + AgentScope** | 面试模拟、出题、评分、复核等多角色流水线；由 Java 通过 HTTP/MQ 调度 |
| RAG / GraphRAG 层 | **Python + LlamaIndex** | 检索路由、混合召回、重排、GraphRAG；底层复用 Neo4j + MySQL |
| 可观测层 | 结构化日志（JSON + trace_id）→ 后续接 OpenTelemetry | 先打通 trace_id，服务拆分后再引入采集平台 |
| 服务间通信 | **HTTP（同步）+ RabbitMQ（异步）** | Java 调 Python 同步用 HTTP，异步任务走 MQ |

### 5.2 本项目的系统拆分建议

| 子系统 | 推荐方案 | 说明 |
|---|---|---|
| 题库与业务 API | Java Spring Boot + MySQL/PostgreSQL | 稳定的 CRUD、权限、事务和治理；长期稳定的主链路 |
| 消息队列 | RabbitMQ | 爬取任务入队、LLM 抽取消费、结果回写；Java 侧统一管理 |
| 智能体编排 | Python + AgentScope | 出题、评分、模拟面试等角色协作；接收 Java 调度 |
| 检索与召回 | Python + LlamaIndex + Neo4j | 统一 RAG 入口，不让各 Agent 自己维护检索逻辑 |
| 检索审计 | `retrieval_event` 表 + 结构化日志 | 记录 query、召回候选、分数、重排结果、模型版本 |
| 日志与链路追踪 | 结构化 JSON 日志（当前）→ OpenTelemetry（服务拆分后） | 先统一 trace_id 规范，再引入采集平台 |

## 6. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| AgentScope 版本升级不兼容 | 编排层需重写 | 锁定依赖版本；评估 LlamaIndex Workflows 作为备选 |
| LlamaIndex 升级 API 变更 | 检索层需适配 | 封装 Retriever 接口，不直接暴露框架 API 给业务层 |
| 单语言栈规模上升后的治理风险 | 并发治理和调优手段较少 | 先做好异步和连接池，到达瓶颈后再评估 Java |
| 检索事件未落库 | 无法回放和审计 | 尽早建立 retrieval_event 表，哪怕只是 JSONL 文件 |
